# 원인 분석 — 직접 확인한 손상과 최초 촉발 원인

[처음으로](../README.md) · [검증 결과](04-validation.md)

## 질문을 나눴다

“왜 Windows가 부팅되지 않았는가”에는 여러 직접적인 근거가 있습니다. “무엇이 처음 그 손상을 만들었는가”에는 아직 연결 증거가 부족합니다. 복구 단계에서 발견한 마지막 오류를 최초 원인으로 바꾸지 않았습니다.

| 설명 후보·관측 | 지지하는 사실 | 반대·제한 근거 | 결론 |
|---|---|---|---|
| 기존 Windows의 논리적 손상으로 부팅 실패 | GPT/NTFS 오류, 0x74, SAM 로드 실패 | 파일별 내부 손상 전수 분석은 없음 | 부팅 실패를 설명하는 확인된 손상들이 존재 |
| 지속적인 SSD 매체 불량 | 디스크 구조 손상 이력은 있음 | 전체 이미지 읽기 성공, SMART 매체 오류 0, Short 통과 | 현재 확정할 수 없음 |
| SSD·컨트롤러·펌웨어·드라이버 상호작용 | NVMe 관리 명령 현상이 새 OS에서도 존재 | 데이터 I/O 실패와 직접 연결되지 않음, 과거부터 존재 | 추가 관찰 단서, 특정 부품 원인 미확정 |
| RAM 문제 | 다층 손상만으로 완전히 제외할 수 없음 | MyASUS 검사 통과, 오프라인 결과 미확인 | 검출된 결함 없음, 배제 완료도 아님 |
| 개발 도구가 디스크를 손상시킴 | 사용 중이었다는 시간적 관련성 | 확보된 조회 기록은 원인 실행을 입증하지 않음 | 특정 프로그램 책임을 지목할 수 없음 |
| 이전 PIN/Hello 문제와 같은 원인 | 선행 인증 오류 기록 | 이후 컨테이너 읽기 성공 지속, 디스크 손상과 연결 증거 없음 | 별도 선행 단서 |
| 복구 USB nwifi.sys가 최초 손상의 원인 | Wi-Fi 연결 시 해당 충돌 화면 존재 | 발생 환경·시점이 최초 장애 이후 | 별도 복구 환경 장애 |
| 정상 사용이 가능하므로 원인이 사라짐 | 새 설치 후 사용 환경 회복 | 간헐적 문제와 새 환경의 이벤트가 남음 | 복구 성공과 원인 규명은 별도 |

검사 없는 후보를 확률 순위로 매기지 않았고, 고장 확률이나 “완치율”도 계산하지 않았습니다.

## 확보 자료의 범위

이전 분석 기록에 따르면 진단 자료는 693개 파일, EVTX 263개, WER 383개, DMP 13개였습니다. System 38,916개 이벤트를 읽고 선택한 38개 로그에서 56,564개 이벤트를 분석용으로 추출했습니다. WER는 실제 시각·ID를 대조해 378개 보고로 구분했습니다.

이는 상당한 조사량이지만 모든 파일을 동일한 깊이로 분석했다는 뜻은 아닙니다. 과거 덤프에는 중복 사본이 있었고, 전부를 WinDbg 심볼 기반으로 완전 분석하지 않았습니다. 최초 장애에 대응하는 새 커널 덤프는 확보 자료에서 확인되지 않았습니다. [E02, E03]

## 인과관계를 막는 빈칸

1. SSD 이미지는 확보 당시 상태입니다. 각 섹터 변경의 실행 주체와 시각을 자동으로 보존한 감사 기록이 아닙니다.
2. 아침 Partition 로그와 이후 이미지의 앞쪽 영역 상태가 다르지만, 최초 충돌 전인지 후속 복구 과정인지 연결할 기록이 부족합니다.
3. PowerShell Operational 로그 하나는 손상돼 Windows API로 읽지 못했습니다. 읽힌 기본 로그의 제한된 검색에서 파괴적 명령을 못 찾았다는 사실은 모든 실행 경로를 조사했다는 뜻이 아닙니다.
4. 당시 WER에 다시 나타난 GPU 관련 보고의 실제 발생 시각은 이전 달이었습니다. 보고된 시각과 장애가 발생한 시각을 구분해야 합니다.
5. 누적 NVMe 관리 명령 이벤트 1,634건(오류 811, 시간초과 823)은 과거부터 있었습니다. 많다는 이유만으로 이번 손상의 원인이 되거나, 오래됐다는 이유만으로 무해한 것도 아닙니다.

## 새 Windows가 더해 준 정보

같은 계열 NVMe 관리 명령 이벤트가 클린 설치 후에도 남았습니다. 따라서 그 현상이 이전 Windows의 손상만으로 생겼다고 설명하기는 어렵습니다.

그러나 이것이 하드웨어 결함의 증명은 아닙니다. 새 설치도 같은 장비·펌웨어·저장장치 동작 환경을 공유합니다. 현재 데이터 오류와 인과관계를 보여 주는 증거가 없어 특정 SSD·메인보드 교체가 필요하다고 결론내리지 않았습니다.

## 정정해 남기는 설명

- 과거 Hello 상담의 “하드웨어 고장이 아니다”, “원인을 특정했다”는 단정은 당시 권한 제한과 검사 범위를 넘어섰습니다.
- 정상 대조군도 실패한 레지스트리 로드 실험은 대상 파일만의 손상 근거가 아니었습니다.
- 표준 권한 Storport 조회의 빈 결과는 관리자 확인 전까지 “오류 없음”으로 사용할 수 없었습니다.
- 메모리 검사 예약과 불확실한 사용자 기억을 검사 통과로 기록하지 않았습니다.
- 센터 점검과 더 강한 검사를 가능한 선택지로 설명하는 것과, 현재 사용을 위해 반드시 해야 한다고 말하는 것은 다릅니다. 후속 대화에서 그 구분을 바로잡았습니다.

**현재 판단:** 사용 환경은 회복됐고, 검사 범위에서 확정된 부품 고장은 없습니다. 최초 촉발 원인은 미확정입니다. 추가 극한 검사를 하지 않고 실제 사용을 재개한 결정과 이 기술적 한계를 함께 보존합니다.
