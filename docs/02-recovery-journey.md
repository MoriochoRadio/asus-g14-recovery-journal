# 고장부터 새 Windows에 로그인하기까지

[처음으로](../README.md) · [타임라인](01-timeline.md)

## SSD는 보이는데 부팅이 안 됐다

오류 화면 뒤에 BIOS로 들어왔을 때 SSD 자체는 인식되고 있었다. 그런데 Windows 부팅 항목이 없었고, 설치 환경에서도 파티션이 보이지 않았다.

바로 초기화하기에는 남겨야 할 자료가 있었다. SystemRescue로 부팅해 ddrescue로 SSD 전체 이미지를 만들었다. 결과는 Finished, rescued 100%, read errors 0이었다. 디스크를 읽는 데는 성공했지만, 이미지에는 이미 손상된 구조도 그대로 들어 있었다.

중요한 자료를 확보한 뒤 복구 작업을 이어갔다. 개인 자료 복구와 개발 작업은 다른 장비에서 따로 진행했다. [E01–E03]

## 파티션 표를 복원하니 다음 화면으로 넘어갔다

이미지에서 주 GPT와 보호 MBR이 손상된 것을 확인했다. 앞쪽 1MiB는 디스크 서명 4바이트를 제외하면 0으로 채워져 있었다. 다행히 디스크 뒤쪽의 백업 GPT는 읽을 수 있었다.

고장 당일 아침 Windows 로그에는 정상적인 파티션 배치가 남아 있었다. 6개 파티션의 위치와 종류, GUID, 속성을 백업 GPT와 비교했더니 일치했다. 이 표를 바탕으로 실제 SSD의 GPT를 복원했다.

다시 조회했을 때 유효한 GPT와 보호 MBR이 인식됐고 CRC 경고도 사라졌다. BIOS에 머물던 상태에서 Windows 자동 복구 화면까지 넘어갔다. 하지만 정상 부팅에는 아직 도달하지 못했다. [E02, E03, E05]

## 파일은 읽을 수 있게 됐지만 Windows는 여전히 멈췄다

WinRE에서 파일을 읽으려 하자 디스크 구조가 손상돼 읽을 수 없다는 메시지가 나왔다. BitLocker는 잠금 해제 상태였다. 암호화 때문에 접근하지 못하는 상황과는 달랐다.

CHKDSK 수리 과정에서 MFT mirror, Attribute Definition Table, Boot File, bitmap, USN 관련 메시지가 나왔다. 수리가 끝나자 OS 볼륨이 NTFS로 인식됐고 디렉터리와 파일 목록을 다시 읽을 수 있었다.

여기까지는 분명히 진전이 있었다. 파티션이 보이고 파일도 읽혔다. 그런데 Windows를 시작하면 다시 오류 화면과 BitLocker 화면이 반복됐다. 자동 재시작을 멈추고 확인한 코드는 **BAD_SYSTEM_CONFIG_INFO(0x74)**였다. [E01, E05]

## 레지스트리 복구를 시도했다

사용할 수 있는 시스템 복원 지점은 없었고 RegBack도 비어 있었다. SYSTEM과 SOFTWARE 파일을 따로 복사해 조사했다.

SYSTEM의 헤더 시퀀스는 360426/360425로 달랐다. 반면 YARP의 구조 검사와 주요 키 조회는 통과했다. SYSTEM.LOG1/LOG2를 반영한 별도 후보도 만들었지만 원본과 로그 사이에 시퀀스 간격이 있었다. 이 후보를 바로 적용하기에는 확신이 부족했다.

정상 PC에서 Windows 로더로 시험했을 때는 정상 대조 파일까지 실패했다. 검사 환경부터 의심해야 하는 결과였다. 실제 노트북 WinRE에서 다시 시험하자 대조군, 원본과 로그의 사본, 후보 SYSTEM, SOFTWARE 모두 로드·조회·언로드에 성공했다.

그래도 후보를 SSD에 덮어쓰지는 않았다. 파일을 로드할 수 있다는 것과 그 구성으로 Windows가 부팅된다는 것은 달랐다. Windows가 검사 사본에 로그를 재적용했을 가능성도 있었다.

마지막 요약 명령인 findstr는 WinRE에 없어 실패했다. 대신 결과 파일을 직접 열어 앞선 검사들이 성공했는지 확인했다. [E06]

## SAM을 읽지 못하는 지점에서 막혔다

BCD의 기본 경로는 Windows 부팅 로더를 가리키고 있었다. 오프라인 SFC는 요청한 작업을 수행할 수 없다는 메시지로 멈췄고, DISM ScanHealth는 0xd000015c로 중단됐다.

처음에는 오류 코드만 보였다. 이후 실제 DISM 로그를 가져와 확인하니 82·84행에 SAM 레지스트리 하이브를 로드하지 못했다는 기록이 있었다. 검사 초기화가 그 파일에서 막힌 것이었다.

이제 어느 지점에서 실패하는지는 알게 됐지만, 처음 무엇이 손상을 일으켰는지는 알 수 없었다. 당시 MEMORY.DMP도 후속 조회에서 찾지 못했고, 확인된 Minidump는 이전 날짜의 것이었다. [E03, E07]

## 기존 환경을 살리는 대신 새로 설치하기로 했다

복구가 길어지면서 많이 지쳤다. 파티션을 되찾고 파일을 읽을 수 있게 만든 뒤에도 Windows는 시작되지 않았다. 이미 필요한 자료를 보존했으니, 기존 환경을 계속 고치는 것보다 다시 쓸 수 있는 상태로 돌아가는 쪽을 택했다.

그런데 ASUS 복구 과정에서도 문제가 생겼다. Cloud Recovery에서는 다운로드만 보였고 실제 복원이 끝나는 모습은 확인하지 못했다. 이어 공식 MyASUS in WinRE USB로 부팅했지만, Wi-Fi를 연결하는 순간 **DRIVER_IRQL_NOT_LESS_OR_EQUAL / nwifi.sys** 오류가 났다.

자동 재부팅 뒤에는 기존의 0x74 화면으로 돌아왔다. 복구 USB의 Wi-Fi 오류와 SSD에 있던 Windows의 부팅 오류가 연달아 보인 셈이다. 새 Windows 설치가 완료된 뒤 같은 오류가 난 상황은 아니었다.

ASUS 복구 경로를 더 반복하지 않고 Microsoft 공식 설치 USB를 만들기로 했다. [E01, E08]

## 설치 USB를 만들고 확인했다

Media Creation Tool 첫 시도는 다운로드 약 33% 뒤 창이 사라졌다. 완료 기록이 없었고 이유도 확인하지 못했다. 두 번째 시도에서는 18:07:49에 MediaCreationSuccess와 종료 코드 0이 남았다.

설치 파일 1,069개는 준비 원본과 USB 사본의 SHA-256이 일치했다. 주요 실행 파일과 EFI 부팅 파일의 Microsoft 서명, 이미지의 언어·에디션·빌드도 확인했다. 분할 SWM은 메타데이터와 크기를 확인했으며 원본 ESD와 바이트 단위로 비교한 것은 아니다.

USB를 다시 쓰기 전에는 그 안의 진단 자료부터 보존했다. 노트북 설치 화면에서 내부 1TB SSD와 설치 USB를 구별한 뒤, 내부 SSD의 기존 파티션을 지우고 Windows를 새로 설치했다.

초기 설정에서는 준비한 공식 Wi-Fi 드라이버를 사용했다. 그리고 Windows에 로그인했다. 이후 노트북에서 조회한 새 설치 시각은 9월 19일 18:32:23이었다. [E09, E10]

## 로그인 후에는 드라이버와 상태를 정리했다

NVIDIA App, Armoury Crate와 평소 쓰던 앱을 설치했다. 점검할 때는 이미 설치한 앱을 반복해서 설치하는 대신 버전과 실제 드라이버 적용 상태를 확인했다.

준비해 둔 공식 설치 파일도 무조건 쓰지는 않았다. 현재 버전이 더 높거나 실제 장치 ID가 맞지 않는 패키지는 제외했다. 누락 드라이버를 설치한 뒤 장치 관리자의 문제 항목은 1개에서 0개로 줄었다.

Windows 시스템 검사와 SSD 자체 검사, MyASUS 진단도 진행했다. 재부팅 전에는 완료한 작업을 파일로 남겼고, 돌아온 뒤에는 새 결과와 비교했다. 상세 수치는 [재설치 후 점검](04-validation.md)에 모았다.

## 어디까지 확인하고 다시 쓸 것인가

Windows가 켜진 뒤에도 마음이 바로 놓이지는 않았다. 부품이 실제로 고장 난 것은 아닌지, 곧 보증이 끝나는데 이대로 써도 되는지 걱정됐다. 센터에 갈 시간과 비용도 부담이었다.

더 긴 검사와 부하 테스트를 할 수도 있었지만, 당장 교체해야 할 고장이 확인된 것은 아니었다. 새로 설치한 상태에서 계속 검사만 하는 대신 평소처럼 쓰기로 했다.

오프라인 메모리 검사와 일부 기능 확인은 남았다. 그 항목들은 기록에 남겨 두고, 실제 문제가 다시 생기면 당시 상황과 새 로그를 확인하기로 했다. [E14]
