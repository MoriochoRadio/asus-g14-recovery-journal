# 복구 여정 — 한 단계의 성공이 전체 복구를 뜻하지 않았다

[처음으로](../README.md) · [의사결정](03-decisions.md)

## 1. 먼저 남길 수 있는 것을 보존했다

처음에는 BIOS에서 SSD가 보이는데도 Windows 부팅 항목이 없었고 설치 환경에서 파티션도 보이지 않았습니다. 곧바로 새로 설치하기 전에 SystemRescue로 부팅해 전체 SSD 이미지를 만들었습니다.

ddrescue 보존 기록은 Finished, rescued 100%, read errors 0이었습니다. 이는 이미지를 확보하는 데 성공했다는 근거입니다. 이미지 안의 파일시스템·파일 내용까지 정상이라는 뜻은 아닙니다. 복구할 개인 자료는 별도로 보존했고, 이후 개발 작업·자료 복구는 다른 장비에서 이어가기로 했습니다. 이 저장소는 그 개인 자료의 내용이나 복구 작업을 공개하지 않습니다. [E01–E03]

## 2. 파티션 표를 되찾았다

이미지에서는 주 GPT와 보호 MBR이 손상돼 있었고 백업 GPT는 읽을 수 있었습니다. 앞쪽 1MiB는 디스크 서명 4바이트를 제외하고 0이었습니다.

백업 표가 있다는 이유만으로 바로 쓰지 않았습니다. 고장 당일 아침 Windows Partition 로그에 기록된 6개 파티션의 시작·끝 위치, 종류, GUID, 속성과 백업 GPT를 비교했습니다. 모두 일치한 뒤 실제 SSD를 확인하고 GPT 복원을 진행했습니다.

작업 후 유효한 GPT와 보호 MBR을 인식했고 CRC 경고가 사라졌습니다. Windows 자동 복구 환경까지 진입할 수 있게 됐지만, 정상 부팅은 되지 않았습니다. 앞쪽 영역이 정확히 언제, 무엇에 의해 바뀌었는지는 끝내 특정하지 못했습니다. [E02, E03, E05]

## 3. 파일시스템 접근을 회복했다

WinRE에서 파일을 읽으려 할 때 디스크 구조가 손상돼 읽을 수 없다는 메시지가 나타났습니다. BitLocker는 잠금 해제 상태였으므로 단순 암호화 잠금과 구분했습니다.

당시 수행한 CHKDSK 수리에는 MFT mirror, Attribute Definition Table, Boot File, MFT/Volume bitmap, USN 관련 수리 메시지가 있었습니다. 이후 OS 볼륨이 NTFS로 인식되고 파일 목록을 읽을 수 있었습니다.

그러나 “0 KB in bad sectors”라는 출력이 모든 SSD 하드웨어를 검증한 결과는 아닙니다. 수리 후에도 기존 Windows는 0x74에서 멈췄습니다. 여기 적힌 명령명은 과거 이력이며 다른 장비에 재실행할 절차가 아닙니다. [E01, E05]

## 4. 레지스트리 후보를 만들었지만 무작정 적용하지 않았다

시스템 복원 지점과 사용할 수 있는 RegBack 백업은 없었습니다. SYSTEM의 헤더 시퀀스는 360426/360425로 불일치했으나 YARP 구조 순회와 주요 키 조회는 통과했습니다.

SYSTEM.LOG1/LOG2를 별도 사본에 반영한 후보도 만들었습니다. 하지만 원본 시퀀스와 유효 로그 사이에 간격이 있었고, 완전한 정상 상태를 재구성했다는 보장은 없었습니다. SOFTWARE의 구조 검사는 통과했습니다.

별도 정상 PC에서 Windows 로더 검사를 시도했을 때는 정상 대조군도 실패했습니다. 그 결과를 파일 손상 증거로 쓰지 않았습니다. 실제 노트북 WinRE에서 대조군·원본+로그 사본·후보 SYSTEM·SOFTWARE를 시험하자 로드·조회·언로드가 성공했습니다.

이 역시 부팅 정상 판정은 아니었습니다. Windows가 검사 사본에 로그를 재적용했을 수 있고 구성 값 전체의 의미를 검증한 것도 아니었습니다. **후보 레지스트리는 실제 SSD에 덮어쓰지 않았습니다.** 마지막 요약에 쓰인 findstr가 WinRE에 없어 실패했지만 실제 결과 파일을 읽어 핵심 검사 성공 여부를 확인했습니다. [E06]

## 5. 기존 Windows 복구의 한계를 확인했다

기존 BCD의 기본 부팅 경로는 Windows 로더를 가리켰습니다. 오프라인 SFC는 요청 작업 수행 불가로 중단됐고 DISM ScanHealth는 0xd000015c로 실패했습니다.

처음에는 오류 코드만으로 정확한 파일을 알 수 없었습니다. 이후 가져온 실제 DISM 로그 82·84행에서 SAM 하이브 로드 실패를 확인했습니다. 이 값은 파일이 레지스트리 형식으로 인정되지 않았다는 상태와 연결됐습니다.

이는 **복구 검사가 어디서 막혔는지**를 특정한 결과입니다. SAM 문제가 최초 사고의 원인이라는 결론도, ScanHealth가 끝나서 수리 불가를 판정했다는 결론도 아닙니다. 당시 MEMORY.DMP는 후속 조회에서 없었고 확인된 Minidump는 이전 날짜의 장애 자료였습니다. [E03, E07]

## 6. 재설치를 결정했지만 ASUS 복구 경로도 막혔다

이미 데이터를 보존했고 기존 환경에는 여러 층의 문제가 있었습니다. 사용자는 길어진 복구 작업으로 지쳤으며, 기존 Windows 보존보다 다시 사용할 수 있는 환경을 우선하기로 결정했습니다.

ASUS Cloud Recovery에서는 다운로드가 보였지만 실제 삭제·복원 완료는 확인되지 않았습니다. 이어 제작한 공식 MyASUS in WinRE USB는 출처·서명·패키지 해시 대조를 통과했으나, 노트북에서 Wi-Fi 연결 중 0xD1/nwifi.sys가 발생했습니다.

그 뒤 기존 0x74 화면으로 돌아왔습니다. 이는 새 Windows를 설치한 뒤 같은 오류가 난 것으로 해석할 수 없습니다. 네트워크 충돌의 덤프·스택은 확보되지 않아 무선랜 칩이나 특정 드라이버 자체의 결함을 확정하지 못했습니다.

같은 경로를 반복하기보다 Microsoft 공식 설치 미디어로 전환했습니다. [E01, E08]

## 7. 설치 USB부터 확인하고 새 Windows로 돌아왔다

Media Creation Tool 첫 시도는 약 33% 뒤 완료 기록 없이 종료됐습니다. 두 번째 시도는 18:07:49 성공 로그와 종료 코드 0을 남겼습니다.

준비 원본과 USB 사본의 설치 파일 1,069개 SHA-256 대조에서 불일치가 없었고 주요 실행 파일과 EFI 부팅 파일의 Microsoft 서명이 유효했습니다. 설치 이미지의 언어·에디션·빌드 및 크기를 확인했습니다. 분할 SWM과 원본 ESD를 바이트 단위로 같다고 검증한 것은 아닙니다.

USB 재작성 전 기존 진단 자료를 보존했습니다. 실제 노트북 설치 화면에서 내부 1TB SSD와 USB를 구별하고 사용자 승인에 따라 기존 파티션을 삭제한 뒤 새 설치를 진행했습니다. OOBE에서는 준비한 공식 Wi-Fi 드라이버를 사용하도록 안내했고 사용자가 Windows 로그인 성공을 보고했습니다. 이후 도구로 새 설치 시각과 장비를 확인했습니다. [E09, E10]

## 8. 설치 성공 뒤에도 적용 상태를 확인했다

사용자가 이미 설치한 NVIDIA App·Armoury Crate·데스크톱 AI 앱을 처음부터 다시 설치하지 않았습니다. 앱 버전, 실제 장치 드라이버, 서비스, 제어 인터페이스를 분리해 조사했습니다.

공식 패키지라도 현재 버전보다 오래됐거나 장치 ID가 맞지 않으면 설치하지 않았습니다. 새 Windows에서는 과거 GPT/CHKDSK/레지스트리 수리 명령을 재실행하지 않았습니다.

드라이버와 보안 업데이트, 누락 장치 해결 후 재부팅 전에 기록을 남겼습니다. 재부팅 후에는 그 기록과 새 결과를 비교했습니다. 자세한 버전과 검증 한계는 [검증 문서](04-validation.md)에 있습니다.

## 9. 복구의 끝을 '검사 무한 반복'으로 정하지 않았다

사용자는 보증 만료 전의 불안과 센터 방문의 시간·비용 부담을 이야기했습니다. 추가 부하 검사가 오히려 부담이 되는지도 질문했습니다.

장시간 부하·오프라인 검사 등 더 할 수 있는 항목은 설명했지만 실제로 모두 수행하지는 않았습니다. 현재 검사에서 즉시 수리해야 할 고장은 확인되지 않았고, 사용자는 추가 극한 부하 검사를 원하지 않았습니다. 일상 사용을 재개하고 실제 증상이 재발할 때 증거를 추가하기로 했습니다.

이 결정은 미확인을 통과로 바꾼 것이 아닙니다. 조사 범위와 사용자 비용을 함께 고려해 작업을 멈춘 것입니다. [E14]
